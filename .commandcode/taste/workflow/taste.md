# workflow
- After editing workspace package source files, do NOT automatically rebuild (`pnpm --filter <pkg> build`) — the user wants to verify changes themselves in dev. Inform them a rebuild may be needed but let them decide when to run it. Confidence: 0.70
- When a project script/tool breaks, fix the root cause in the script rather than manually executing the commands it would run. The user prefers durable fixes over one-off workarounds. Confidence: 0.80
- When modifying workspace package structure (adding/removing packages, changing dependencies), do NOT run `pnpm install` — only update the package.json and workspace config files. The user handles installation themselves, likely because their environment requires specific conditions for install to succeed. Confidence: 0.75
- When configuring deployment or infrastructure (e.g., Cloudflare Workers vs Pages targets), verify the actual deployment platform from the repository's configuration (wrangler configs, deploy workflows, app structure) rather than assuming. Check the repo first. Confidence: 0.70
- Prefers tracer-bullet vertical slices over horizontal/architectural layers when breaking a spec into tickets — each ticket should deliver independently verifiable value with clear blocking dependencies. Include a dependency graph showing what can run in parallel. Confidence: 0.60
- When publishing plans, tickets, or sub-issue breakdowns, propose the plan for review and approval BEFORE creating/publishing — do not create first and explain after. Confidence: 0.65
- When reverting/undoing changes, scope the revert surgically to only the files and paths affected by the specific change being undone. Do NOT use broad `git checkout` of entire directories or wildcard paths that could clobber unrelated pending work. The user expects precision — if the rename touched 61 files, revert only those 61 files, not everything in the repo. Confidence: 0.75
- During mid-flight refactors, commit fully to the new direction — do not try to preserve backward compatibility with old names, old APIs, or deprecated patterns. When the user renamed methods and removed code intentionally, complete the migration (update all consumers to the new API) rather than patching gaps with compat shims or suggesting reverting to old names. Confidence: 0.75
- When architectural patterns are removed (e.g., `withFreshDb`, DB-backed cache), project documentation (AGENTS.md, CONTEXT.md) must be updated to match — delete stale references proactively. Documentation drift is technical debt; AGENTS.md should be the accurate source of truth for the project's architecture and conventions. Confidence: 0.65
- When a significant architectural decision (ADR-worthy) surfaces during a working session, fork it into a separate dedicated conversation rather than handling it inline. The user prefers to keep implementation sessions focused; major decisions with trade-offs and documentation get their own thread. Multiple ADR candidates from the same session can each go to separate conversations. Confidence: 0.70
- Prefers testing at both the handler/API boundary (integration-level, mocking the data layer module) AND the data-layer boundary (unit-level, mocking the Prisma client) — especially when security-critical invariants like tenant isolation (ownerId scoping) live in the data layer and can only be verified there. A single seam is not sufficient when the invariant crosses a boundary. Confidence: 0.70
- When the user announces a "grilling session" (structured interrogation/Q&A to test understanding of the codebase), do NOT start analyzing or exploring anything until they explicitly give the go-ahead — just acknowledge and wait. The user wants to control when analysis begins themselves. Confidence: 0.65
- Deploys via GitHub Actions workflows (`.github/workflows/deploy-api.yml`, `deploy-web.yml`), not Cloudflare Pages build hooks — deploy-time steps like `prisma migrate deploy` and seed commands belong in those workflows, using GitHub secrets. Factor this into infrastructure/deploy decisions rather than assuming Cloudflare's build sandbox runs them. Confidence: 0.9
- Prefers keeping reusable QA/testing utilities (e.g., test-user seed scripts, browser-QA guides) committed in the repo as durable artifacts rather than treating them as throwaway one-off scripts — they should be reusable by future AI agents/sessions. Confidence: 0.75
- During QA/testing against a database that contains real user data, do NOT mutate existing records (e.g., reassigning `ownerId`/ownership via `updateMany` to test accounts). Real user data is sacrosanct — use isolated test rows or a separate test DB, and restore anything touched. Confidence: 0.8
- PRs target the `dev` branch (not `main`/`master`); merging to `dev` deploys to the development environment. `dev` is the active integration branch for development work. Confidence: 0.8
- When opening a PR, write a descriptive title AND body that accurately represent the changes made (the user explicitly asks for both) — avoid generic/placeholder titles, and note any caveats like extra commits dragged into the diff. Confidence: 0.6
- When a bug is caused by externally-corrupted/stale state (e.g., a Stripe webhook that never fired in local dev leaving a `trialing` subscription frozen in the DB), prefer cleaning up the local data directly over adding defensive reconciliation or guard code to mask the symptom. The user considers masking code unnecessary when the root cause is environmental rather than a logic defect. Confidence: 0.70
- When asked to analyze an option/approach before implementing, do a rigorous code-level analysis first: verify assumptions against the actual code (schema, indexes, callers, tests, docs) rather than relying on prior context or prior hypotheses, and present what each option does and does NOT cover before touching code. Confidence: 0.65
- For large migrations/rewrites, prefers incremental route-by-route (vertical slice) delivery with every stage kept buildable and CI green (type-check, lint, tests, build), plus a single final production cutover — explicitly avoids running two implementations side by side in production. Confidence: 0.60
- When rewriting existing functionality, defaults to visible behavior/design parity and documents UX improvements rather than bundling them into the migration; only architecturally necessary improvements are applied while porting, so migration, behavior change and redesign stay separate. Confidence: 0.65
- Expects the quality bar for a frontend rework/cutover to include unit tests for logic/composables, critical-path E2E flows, and visual QA at mobile (375px) and desktop (1280px) breakpoints. Confidence: 0.55
- Works from a numbered roadmap of sequenced tasks: the parent roadmap lives at `~/.commandcode/plans/<project>.md`, each task session gets its own plan file in that same directory (written and approved before code), and the session closes by writing a durable task file under `docs/tasks/` recording scope, dependencies, deviations, verification evidence, rollback and follow-ups. Confidence: 0.6
- Before starting a task in a multi-task roadmap, explicitly verify that the previous tasks are actually in the repo/HEAD (git log + status, read their task files and ADRs) instead of assuming — the user explicitly asks for all the previous work to be checked first ("but first check all the previous work done", "check previous work done if needed"), and a brief "work in the task N" alone is enough to trigger that context-gathering, and a bare "continue with task N … check any previous work if required" is a typical instance. Confidence: 0.8
- Expects a complete verification gate before committing: per-package tests, then root `lint`, `type-check`, full `test` and `build` all green, plus `git status` showing only files belonging to the task. When no UI is touched, explicitly state that visual/responsive QA is not applicable rather than running the dev server. Confidence: 0.6
- Prefers hermetic e2e tests for a frontend that talks to an upstream API: a local stub server started by the test runner's `globalSetup` (no real DB, no external network), with unit tests covering the real transport branch and a documented manual smoke (`wrangler dev`) as the only check that hits the actual runtime — over running e2e against the real API/DB (fragile in CI, risk of mutating data). Confidence: 0.6
- For authenticated visual QA, prefers creating a throwaway test user seeded into the dev database (following the documented seed/browser-QA practice) rather than mocking the session or asking for real credentials. Confidence: 0.55
- When a test fails after a change, prove whether it is pre-existing before reporting it: re-run that test at HEAD (e.g., stash the change) and report the finding explicitly instead of silently fixing or blaming it on the new work. Confidence: 0.65
- The local shell loads `.env` and exports `WEB_ORIGIN`/`BETTER_AUTH_URL`/`PUBLIC_APP_URL`, so env-dependent tests must be run with those unset (`env -u ... pnpm ...`) to match CI's clean environment — otherwise pre-existing failures appear as if caused by the change. Confidence: 0.6
- After QA/smoke sessions that spawn dev servers, workers, or stub processes, kill everything you started and free the ports, then restore any dev config you temporarily modified (e.g., `.dev.vars` `INTERNAL_API_URL`). Explicitly leave processes that were already running before the session untouched and say so. Expected to verify port/process state at the end. Confidence: 0.6
- Once a task's plan is documented/approved and there are pending checklist items, continue executing the task autonomously through its remaining steps rather than stopping to re-confirm direction at each point ("continúa con lo establecido en la tarea"). An explicit approval ("approve plan") covers the plan's delivery steps too: thematic commits with the secret/absolute-path gate, push, PR to `dev`, watching and retrying CI, merging (which deploys staging) and smoking the deployment — the user is not asked to re-authorize each one. Only surface a question when a genuinely new decision is required (e.g., a blocking pre-existing bug). Confidence: 0.6
- When delegating a scoped fix mode (e.g. `/design recolor <file>`), the user spells out the invariants, the expected evidence (a measured matrix for the whole cross-product and a unit test that locks the contract), a runnable acceptance command (the previously-failing a11y sweep going green), and an explicit out-of-scope fence — and expects the change to stay strictly inside that fence, with any gap found outside it declared as a follow-up rather than silently fixed. Confidence: 0.6
- Fix a blocking/preexisting bug before advancing to the next planned task or feature — the user replies "soluciona el bug primero antes de continuar" when the assistant offers to defer it in favor of the next roadmap task. Known blockers take priority over new scope. Confidence: 0.7
- For visual QA with agent-browser, do not rely on reading several screenshots in one go (multi-image reads are unreliable): inspect one capture per state and verify the remaining states via DOM `eval` (geometry, texts, `data-*` markers), keeping the screenshots in a gitignored `test-results/qa/` folder as evidence. Confidence: 0.6
- The repo is Prettier-clean: run Prettier (`pnpm exec prettier --write`) over the files touched by the task before committing, but never let formatter churn bleed into unrelated parts of pre-existing files — revert the noise and re-apply only the intended edits so the diff stays scoped to the task. Confidence: 0.6
- Wants surfaced technical/UX debt ("deudas honestas" reported at the end of a task) explained concretely and then actually paid down, rather than left as documented follow-ups — when the session summary lists pending items, expect a follow-up request to explain and improve them ("revisa los detalles que encontraste para atenderlos"). Each item should end resolved or explicitly declined with a measured reason, never re-deferred. Confidence: 0.7
- When porting a feature whose baseline fetches everything up front, prefers re-architecting it to load only what the screen needs (on demand, in chunks, cached in memory) over reproducing the baseline for parity — even when that fixes a latent scale bug (the legacy page 400'd past 100 records) and changes the legacy data flow. Visible behaviour stays at parity; the loading architecture is allowed to improve. Confidence: 0.55
- When porting legacy functionality, normalize internal API contracts to the project's current standard (JSON request body validated with the shared Zod schema + the common error envelope) rather than faithfully preserving the legacy contract (FormData bodies, `c.text`/raw-string errors, `{ok:false}` responses) — the user chose the "JSON + envelope + Zod" option over a FormData/parity one. The visible-behavior parity default applies to UX, not to internal plumbing when the old consumer is being retired. Confidence: 0.65
- During a migration, do NOT carry over dead/inactive UI (e.g., JS with no markup, hidden or disabled forms). Leave it out of the port and record it as a finding instead of reproducing it for completeness' sake. Confidence: 0.55
- When a roadmap task's scope is large enough to risk exhausting a single session (QA + cutover + cleanup + docs), prefers splitting it into two sequentially-planned sub-tasks (e.g. Task 13 → 13a = QA integral + CI gates, 13b = cutover, Astro retirement and docs), each with its own approved plan, task file and closure, over one long session — explicitly to keep room for careful verification. Confidence: 0.6
- For CI/CD of a monorepo with a web app and an API, prefers consolidating the per-app workflows into a single `deploy.yml` whose jobs are chained by dependencies (verify → deploy-api → deploy-web), so the API deploys before the web app and all checks run against the same commit — over separate workflows linked with `workflow_run` (duplicated verify, extra indirection) or leaving the API→web order documented but unenforced. Confidence: 0.6
- Expects CI to block on everything deterministic: lint, type-check, unit/nuxt tests, build, `wrangler deploy --dry-run`, the full e2e suite on chromium plus a critical-journey smoke on firefox and webkit (checking console errors, hydration warnings and 5xx), and the axe accessibility scans. Visual QA stays manual (375/1280 captures + DOM checks as evidence), and blocking Lighthouse audits or `toHaveScreenshot` visual-regression baselines are explicitly declined as too slow/flaky for the pipeline. Confidence: 0.6
- For features that depend on real third parties (Google OAuth callback, Stripe checkout, cookies/CSRF, host allowlist), prefers a guided staging pass: the agent deploys a throwaway worker against the staging API when Wrangler credentials are available and documents evidence while the user does the click-through — rather than deferring to a written runbook or an agent-only local `wrangler dev` smoke that never exercises the real integrations. Confidence: 0.55
- When a session reports findings/follow-ups ("hallazgos"), the user expects each one to be durably annotated (in the task file / AGENTS.md, not just the chat) and routed to its concrete owner — the specific future roadmap task/session it belongs to (or a quick ad-hoc fix) — noting the file where it manifests so future sessions can identify it and decide whether that task resolves it or it gets covered by the adjustments that task will make. Confidence: 0.7

- When a quality gate fails across many combinations (e.g. an axe sweep over accents × themes), does not fix the first reported case: build a temporary non-failing diagnostic that enumerates the complete inventory of violations, fix the systemic pattern across every usage in the codebase, then delete the temp spec and widen the permanent gate to cover the surfaces/combos that were previously missing. - When running authenticated CLIs (`wrangler`), credentials are exported from the local env file into shell env vars for the command and never printed — verify auth by echoing presence/sizes (token/account length) rather than the values, and report the target account/env instead. Confidence: 0.55
- `/design review` is a report-only mode: when invoked, produce the review artifacts (`.commandcode/design/review-report.md` plus a self-contained `.html` of the same verdict/report) and do NOT modify product code in that turn — the resulting findings are routed to a scoped follow-up mode with an explicit acceptance gate instead (e.g. a `/design recolor` limited to the token module, accepted only when the failing a11y sweep goes green). Findings must be backed by measured evidence (computed styles, axe runs) with the exact file/line, not appearance guesses. Confidence: 0.6

Confidence: 0.6
- Pasting a raw CI failure log with no instruction is a request to fix it end-to-end: reproduce the root cause, fix it durably in the repo (script/config, not a local workaround), commit it as its own scoped commit on the open branch, push, and follow the CI run until the checks are green — then report the outcome without asking for permission at each step. - Treats CI as the real environment: a local green run is not evidence when generated artifacts differ, so reproduce CI failures from a genuinely clean state (delete `.nuxt`/`.output` first, and re-check that they haven't been regenerated before trusting a verification run). Confidence: 0.6
- Cross-checks work produced by other AI tools: pastes a full plan/spec drafted elsewhere ("hice un análisis con otra IA") or a UI variant they solicited from another model ("le mandé tu resultado a Claude", pasted as a screenshot) and asks what could be improved / whether the approach is right, expecting the agent to audit it against the actual code — keep what is correct, flag what is misplaced (wrong location for a route, dead code, unnecessary changes to public contracts) and the missing pieces — before any code is written. A pasted design is judged against the repo's own vocabulary (DESIGN.md, sibling components: whether a word like "tanda" exists in the app, whether color is carrying meaning on data, whether sliders are a pattern the product has), the agent states explicitly when the variant is not in the tree and it is judging from the capture alone, and closes by offering to apply the agreed fixes on the tree. - For a bug fix, the new regression test is not considered done until it has been shown to actually catch the bug: temporarily disable/short-circuit the fix, confirm the test fails, then restore it (mutation check). A regression test that passes with and without the fix proves nothing. Confidence: 0.5
- Pre-existing processes left over from earlier sessions are expendable when they are wedged and block the work: faced with stale Nuxt/worker processes (a day old, accepting connections but never responding, so SSR hangs) holding the dev ports, the user chose "matarlos y levantar limpio" — kill the whole process tree and start a fresh dev server — over working around them on alternate ports or downgrading to a code-only review with no rendered evidence. The "don't touch what was already running" rule applies to healthy processes, not to ones that block verification. Confidence: 0.6
- When asked to remediate everything found in a review/audit ("genera un plan para atender todos los problemas"), expects a single plan file whose tasks are each runnable in its own separate session: every task names the exact command/skill to invoke (the design mode, repo skills, QA tooling), its file:line scope, its own verification commands and a measurable acceptance criterion, plus a ready-to-paste session start prompt — and asks for these commands/skills to be spelled out explicitly in the plan so the corrections can be launched across multiple sessions. Include a dependency table/notes so tasks can run in any order that respects dependencies. Confidence: 0.7
- Works test-first (TDD): the first step of a task is a red contract test that encodes the invariant (e.g. accent-as-text ≥ 4.5:1 across the 7 families × 2 themes, written before the token exists), confirmed failing, then the implementation turns it green — the repo ships a `tdd` skill and the plan orders the steps rojo → implementación → verde. Confidence: 0.55

Confidence: 0.55
- Stages changes file by file (never a blanket `git add` of everything) so work in progress from another session in the same worktree stays untouched, and confirms that explicitly in the closing summary. When a single file itself mixes both sessions' edits, stage only your own hunks (filter your diff into a patch and `git apply --cached` it), leaving the other session's hunks unstaged and untouched. Confidence: 0.55
- Visual QA of a responsive surface covers the full breakpoint matrix (320/375/768/1024/1280) in both light and dark themes — not only the 375/1280 pair — with the captures kept as gitignored evidence and every numerical claim re-measured in the DOM. Confidence: 0.55
- A copy/text change is verified by measurement, not by reading it: inject the previous string into the same node (`el.textContent = old`) and compare line counts (`Range.getClientRects()` with height > 1) at mobile and desktop widths in both themes, so "the block does not grow" is evidence rather than an impression — and the new copy is shortened when it does grow (a 81→65-character subtitle to keep the closing band's paragraph at 2 lines on mobile). The same pass asserts the absence of the removed string in the server-rendered HTML of every surface that shows it. Confidence: 0.5

Confidence: 0.6

Confidence: 0.6

The added risk/scope (research spikes, a validation gate before committing to the unknown) is acceptable when the payoff is the real fix. Confidence: 0.5
- Plans for a structurally risky change carry: a task dependency table (what is parallel-safe), a first *gate* task that proves the risky premise with numeric acceptance criteria and an explicit stop condition ("if the gate fails, do the smaller fix and stop"), a rollback section stating exactly how to undo ("revert the commit; `DATABASE_URL` does not change") and a risk table with mitigations. Confidence: 0.55
- Performance/latency claims are settled by measurement in the real runtime, not by theory: per-operation timings for the current path, the same measurement for the alternative being rejected (e.g. a module-scope TCP client hangs: 46 s plus a cancelled request), before/after end-to-end numbers for the fix (webhook 18-60 s with 500s → 3.2-3.6 s local, 3.7-4.3 s staging) and the honest counter-evidence (light requests got slower: sign-in 1.01 → 1.19 s) reported alongside the win. Confidence: 0.6
