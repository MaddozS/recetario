# nuxt
- Feature components under `app/features/**` are NOT auto-imported (only the shared UI kit under `~/components/ui` and landing are): every feature component must be imported explicitly. A missing import silently renders nothing and `nuxt typecheck` does not catch it — the component tests do. Confidence: 0.6
- `refreshNuxtData("<key>")` issued from a DIFFERENT page is a no-op, and a fixed `useAsyncData` key does NOT block a refetch on remount: `useAsyncData` registers an `app:data:refresh` hook that `_off()` unregisters when the page unmounts, `getDefaultCachedData` only returns payload-extraction data (inactive here), and `experimental.purgeCachedData` defaults to `true` (`nuxt@4.5.2`), so the unmounting page purges its entry and a list refetches by itself when remounted. Consequence: a slice that mutates data and returns to a list page should use the mutation response for its own state and let the list refetch on remount — do NOT call `refreshNuxtData` for it (verified in Task 9; supersedes the earlier Task 8 note). Confidence: 0.75
- Shareable list filters live in the route query (e.g. `?category=`; empty string = "uncategorized", absent = all) and are updated with `navigateTo`, so deep links, back/forward and SSR filtering work for free and no refetch occurs. Ephemeral, feedback-only query params that the legacy page generated itself in its own redirects (e.g. `?type=`, `?message=`, `?upgrade=1`) are dropped rather than ported. When the query holds frequently-toggled selection state (checkbox toggles, quantity steppers), write it with `{ replace: true }` (parity with Astro's `history.replaceState`) so history isn't flooded, and derive the initial view/stage from the query so a deep link SSRs the same view the client hydrates. Confidence: 0.55
- Await `useAsyncData(...)` inside async composables/`setup` and register lifecycle hooks (`onMounted`…) BEFORE the first `await`: not awaiting makes the server render the initial (empty) state while the client hydrates the fetched data, causing a hydration mismatch (`Hydration completed but contains mismatches`) that production builds don't explain — diagnose it in dev; and after an `await` Vue has no component instance to attach the hook to. Confidence: 0.7
- Data a layout needs for its first render (e.g. the breadcrumb label derived from a record) must be resolved in a route middleware, not in the page's setup: the layout renders (its header included) before the page's setup runs, so a page-set `useState`/`watch` arrives after SSR painted the fallback and the client hydrates with the real value → "Hydration completed but contains mismatches". Resolve it in middleware and reuse the page's `useAsyncData` key (e.g. `recipe:<id>`) so there is no second request. Confidence: 0.6
- Post-mutation state follows a single-writer, derived-state pattern: the detail composable owns the record and exposes one writer (`applyRecipe(next)`); sub-feature composables call it with the API response, and everything derived (financial rows, batch cost, per-piece cost/price/margin) is a `computed` over that record — so mutations recalculate in place with no page reload, no DOM patching and no duplicated parallel state. Validate in the composable (pure modules, zero requests on invalid input) and let presentational components only render the `MutationOutcome`. Confidence: 0.6
- Internal navigation uses `<NuxtLink>`; a raw `<a href>` for a same-origin route turns every click into a full-document SSR reload (no `page:loading:*` hooks, no chunk prefetch, session re-bootstrap per click), which is exactly the "the click seems to do nothing / the first visit is slow" latency users report. Raw `<a>` is reserved for external URLs, non-HTTP protocols (`mailto:`/`tel:`), same-page hash anchors and the `/api/**` relay — a shared `isInternalHref(href)` helper in `#shared/utils/navigation` encodes the rule. `NuxtLink` still renders a real `<a href>` (class/attrs preserved) so DOM/href-based tests keep passing, though component specs without a router may need a `NuxtLink` stub. Confidence: 0.6
- A data-fetching route middleware must be a no-op on the client (`if (!import.meta.server) return`): the SSR pass still resolves before render and can redirect there (identical HTML), while client navigations stop blocking and the page fills the value reactively when the datum arrives (e.g. `useBreadcrumbTail`). Sharing the `useAsyncData` key with the page keeps it to a single request. Confidence: 0.6
- Switching a page's `useAsyncData` to `lazy: true` needs two compensating changes: an explicit `idle` state (the previous `default: () => ({ status: "failed" })` is indistinguishable from a real error while loading), and a `watch(..., { flush: "sync" })` for anything seeded from the data — a deferred watcher seeds a tick late, so SSR paints the empty form / selector stage while the client hydrates the other one (hydration mismatch, and `?edit=true` / `?recipes=…` deep links break). Confidence: 0.55
- `router.afterEach` / `page:loading:end` fire when the route *resolves*, not when the page's data arrives; with `lazy` data that is tens of ms, so a pending-style state cleared on those hooks is imperceptible. Keep it visible for a minimum window (~500 ms, the same criterion as the progress indicator's `hideDelay`), ignore the initial navigation, and skip duplicate-route clicks (Vue Router aborts them without firing `afterEach`, which would leave the state stuck). Confidence: 0.5
- Session/subscription freshness in an SSR SPA is handled by explicit client revalidation, never by refetching on navigation: the auth snapshot is resolved once per document (SSR bootstrap `event.context.auth` → `useState("auth")`, via a builder shared between server and client) and a client plugin revalidates it on `pageshow` with `persisted` (bfcache restore, forced), `visibilitychange` (→ visible) and `focus`, funneled through a pure scheduler with a TTL (~30 s) plus in-flight dedupe — a network failure keeps the snapshot (best-effort), a `null` session expires it, and the initial load does not fire (SSR already seeded). Freshness of a derived resource is decoupled from the mount query: the billing tab always revalidates `/api/billing/subscription` on activation and on session revision, using the session snapshot only as first paint/fallback. Refreshing the session on every SPA navigation (`router.afterEach → refresh()`) was explicitly rejected as needless per-nav requests, and `Cache-Control: private, no-store` / bfcache were left untouched — revalidate on restore instead of penalizing navigation. Confidence: 0.5
