# architecture
- Prefers UI components, TypeScript utilities, and CSS tokens to live co-located inside the consuming app (`apps/web/src/components/`, `src/lib/`, `src/styles/`) rather than extracted into a separate shared package (`packages/ui`). Rejects premature extraction into workspace packages when there's only a single consumer — co-location and simplicity take priority over future-proofing abstractions. Confidence: 0.95
- When a pattern introduces complexity (e.g., per-request PrismaClient via `withFreshDb`) but the theoretical benefit hasn't materialized as a real problem, the user will choose to remove the complexity and use the simpler approach (e.g., the Prisma singleton). Even if the complex pattern was documented as the intended design in AGENTS.md, if it was never properly wired up and the simpler alternative works, rip out the complexity rather than finish the plumbing. Pragmatism over theoretical correctness. Confidence: 0.80
- Password reset and email verification are separate concerns — resetting a password MUST NOT automatically mark the account's email as verified. Do not call `prisma.user.update({ data: { emailVerified: true } })` (or equivalent) as a side effect of the password-reset flow. Confidence: 0.90
- During password-reset flows, do NOT use session-requiring framework APIs (e.g., `auth.api.changePassword`) — the user is not authenticated. Instead, use the framework's own crypto utilities (e.g., `hashPassword` from `better-auth/crypto`) to hash the password and update the underlying account store directly via the data layer (e.g., Prisma `account.updateMany`). This maintains password-hash compatibility without needing a session. Confidence: 0.70
- Email-based action links (password reset, email verification) should point users to the **web app** origin, not the API origin. The web page then calls the API validation endpoint via fetch. Use `WEB_ORIGIN` and `API_URL` env vars (with sensible localhost defaults) so the callback can rewrite the URL. Follow the pattern established by the existing verification-email-callback. Confidence: 0.80
- Data-access/DB packages should be pure persistence (CRUD, ownership scoping, transactions). Validation, normalization/response-shaping, and business logic belong in the consuming API layer — not in the DB package. This applies universally: domain entities AND infra concerns (billing plans, audit logs, account updates, usage counts). The db package is mechanically thin; the API owns all decision logic ("why" vs "what"). When refactoring, move validation and normalization out of the data layer into the API; the DB package's job is to talk to the database, nothing more. Confidence: 0.90
- The API must never import or use `prisma` directly — every data access goes through a `@recetario/db` package method. This applies universally: domain entities (recipes, ingredients, presentations) AND infra concerns (billing plans, audit logs, account updates, usage counts, preferences). `prisma` remains exported from `@recetario/db` for the one workspace package that genuinely needs the raw client: `packages/auth` (needs it for Better Auth's `prismaAdapter`). `packages/billing` should also have its prisma calls moved to `@recetario/db` CRUD methods — auth is the sole exception. The boundary: `apps/api` and `packages/billing` are forbidden from importing `prisma`; only `packages/auth` keeps the raw client. Confidence: 0.90
- All `@recetario/db` methods follow a strict `actionNoun` naming convention: `get`, `create`, `update`, `delete` as verb prefixes (e.g., `getRecipe`, `createIngredient`, `updateRecipe`, `deletePresentation`). No `list` prefix — collection reads use `get` too (e.g., `getIngredients`, not `listIngredients`). Domain-specific verbs `duplicate` and `upsert` are also allowed where CRUD verbs don't fit naturally (e.g., `duplicateRecipe`, `upsertUserPreferences`). The db package naming is canonical: when an API handler import name conflicts, the db method name wins and the API import is updated to match. Confidence: 0.90
- Tenant isolation (`ownerId` scoping) must be enforced in the db package as the single enforcement point — every domain CRUD method that touches a tenant-owned record must take `ownerId` as a parameter and scope its `where` clause by it. The API layer must never add `ownerId` manually to queries; it relies on the db method already requiring it. Any existing db reader that lacks `ownerId` scoping (e.g., `getIngredient(id)` without ownerId) is a cross-tenant read hole that must be fixed. Confidence: 0.75
- When the web app dev server proxies `/api/*` to the API worker (common in monorepo setups), rewriting only the origin is insufficient — you must also rewrite the API path prefix (e.g., `/api/auth/reset-password` → `/reset-password`). Otherwise the proxy intercepts the request and forwards it to the API, returning JSON instead of the UI page. Confidence: 0.75
- Seed data scripts (e.g., subscription plan seeding, `syncPlansFromStripe`) belong in the `packages/db` package — the data layer owns seeding, even when the seed involves external API calls (Stripe) alongside CRUD. Domain packages like `packages/billing` should not host seed logic; they call db methods for CRUD but don't own data initialization. Confidence: 0.95
- Prefers naming workspace packages after the concrete external service they wrap rather than an abstract domain name (e.g., rename `billing` → `stripe`). A package whose job is talking to Stripe should be called `stripe`. Confidence: 0.60
- The db package should define nothing of the external integration — no Stripe singleton, no stripe imports, no runtime code that calls the Stripe API. The Stripe client and Stripe-specific logic belong in the stripe/billing package, and the API consumes db for persistence only, importing the stripe package directly just where Stripe-specific handling is required (e.g., the webhook route). The single permitted exception: the seed script under `packages/db/prisma/` is the ONLY place in the db package that imports the external service package — nothing else in db may require it. Confidence: 0.90
- Seeding/bootstrap of reference data (e.g., subscription plans) is a production concern, not just dev tooling — when a seed is introduced, the user wants it available in BOTH dev and prod, so production seeding must be explicitly accounted for. Do not treat seeds as dev-only conveniences or leave prod bootstrap to a runtime auto-seed on first request. When offered the prod seeding mechanisms, the user explicitly chose a deploy-pipeline/build-time step (alongside `prisma migrate deploy`) over a scheduled cron in the worker or a manual ops command. Confidence: 0.85
- Entitlement/subscription reads on the hot path (session middleware → every authenticated page) should be **uncached** — stale entitlements after a plan change produce inconsistent UI, which is worse than the cost of a cheap indexed query. Correctness wins over edge caching for state that gates features/limits. Confidence: 0.70
- Prefers choosing a frontend framework by matching it to the app's actual nature: for a data-heavy, frequently-mutating UI (not a content/marketing site), static-content-first frameworks like Astro are a poor fit; prefers reactive, stateful frameworks with strong ecosystem and "enterprise use" (e.g., Vue/Nuxt). In framework-selection discussions, value enterprise adoption/long-term maintenance as a factor, and separate the framework-fit decision from SEO/product needs and rewrite cost; a larger ecosystem/hiring market alone (e.g., React) does not justify adopting a model the user likes less. Confirmed on Recetario: a full Nuxt 4 (Vue) rewrite, chosen primarily for readability/legibility, with SEO treated as a cross-cutting requirement rather than the reason to migrate. Confidence: 0.80
- Prefers organizing frontend code by feature/domain — each domain groups its page, components, composables and utils together, extracting to a shared folder only what is actually reused — instead of global type-based folders (`components/`, `composables/`, `stores/`, `utils/`). Atomic Design is reserved for the shared visual UI layer (atoms/molecules/organisms) while business logic stays with its feature (hybrid). Chosen explicitly in the name of legibility. Confidence: 0.65
- Prefers local-first state management in the frontend: component-local `ref`/`computed` and feature composables by default; a global store (e.g., Pinia) only for state genuinely shared across routes (session, preferences). Avoids turning every resource into a global store. Confidence: 0.60
- Keeps the backend API authoritative: business validation, permissions and mutations stay in the backend service (e.g., Hono); an SSR frontend framework is expected to handle UI/SSR/routing/proxy only, not to become a second BFF backend with its own validation or aggregation logic. Confidence: 0.60
- When a piece of logic already lives in a workspace package but reaching it through the package's barrel would drag heavy/server-only dependencies into the new consumer's bundle (e.g. the Stripe SDK, Prisma), prefer adding a dedicated additive *subpath* export for the pure module (e.g. `"./subscription": "./src/subscription.ts"`) and importing that, instead of duplicating the logic locally in the consumer. One source of truth, without embedding the heavy dependency. Confidence: 0.6
- Cross-cutting mutation policy belongs in the API, not only in the frontend UI: CSRF (trusted origin plus double-submit token on every mutating method), plan limits and feature gates must be enforced server-side so a direct API call cannot bypass them; entitlement reads fail closed (no subscription row → free plan). Error codes must stay differentiated (e.g., `PLAN_LIMIT` vs `FEATURE_REQUIRED`) so the UI can react differently to plan limits than to generic failures. Confidence: 0.65
- Do not import a workspace package's barrel or client entry point when its module-level side effects drag a heavy/server-only dependency into the browser bundle. In the Nuxt web app the auth flows deliberately avoid `@recetario/auth/client` (importing it runs `createAuthClient` and pulls `better-auth` into the client chunk); they call `/api/auth/**` through a typed feature client over `useRequestFetch()` with their own error normalizer, and pure validators come from the additive `@recetario/auth/password` subpath. Every build is checked with a grep of the client bundle for forbidden deps (`better-auth`, Prisma, `@recetario/db`, `node:crypto`). Confidence: 0.6
- Pages whose URL carries a secret (password-reset token, email-verification token) must be `noindex, nofollow`, must not emit canonical or OG metadata (tokens/emails never reach metadata or the sitemap), and the server middleware must send `cache-control: private, no-store` + `x-robots-tag: noindex, nofollow` as defence in depth against shared caches. Confidence: 0.6
- After a successful client-side sign-in, navigate with a full page load (`navigateTo(target, { external: true })`, equivalent to Astro's `window.location.href`) instead of a soft client navigation, so SSR re-resolves the session — otherwise the stale session state makes route middleware bounce the user back to `/sign-in`. Confidence: 0.6
- Derive API record types from the shared Zod schema (`type IngredientRecord = z.infer<typeof ingredientSchema>`) instead of importing a hand-written interface that can drift from the contract — the schema is the single source of truth (it models nullable `brand`/`supplier`, which the hand-written type did not). Confidence: 0.55
- Extend shared UI-kit components additively rather than forking a per-feature variant: new *optional* props whose defaults reproduce today's behavior exactly (e.g. `Dialog` gains `size?: "md" | "lg" | "xl"` and `scroll?: boolean`, defaulting to the existing look), with tests covering both the default and the new combinations so existing consumers don't regress. Confidence: 0.55
