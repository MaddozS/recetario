# architecture
- Prefers UI components, TypeScript utilities, and CSS tokens to live co-located inside the consuming app (`apps/web/src/components/`, `src/lib/`, `src/styles/`) rather than extracted into a separate shared package (`packages/ui`). Rejects premature extraction into workspace packages when there's only a single consumer — co-location and simplicity take priority over future-proofing abstractions. Confidence: 0.95
- When a pattern introduces complexity (e.g., per-request PrismaClient via `withFreshDb`) but the theoretical benefit hasn't materialized as a real problem, the user will choose to remove the complexity and use the simpler approach (e.g., the Prisma singleton). Even if the complex pattern was documented as the intended design in AGENTS.md, if it was never properly wired up and the simpler alternative works, rip out the complexity rather than finish the plumbing. Pragmatism over theoretical correctness. Confidence: 0.80
- Password reset and email verification are separate concerns — resetting a password MUST NOT automatically mark the account's email as verified. Do not call `prisma.user.update({ data: { emailVerified: true } })` (or equivalent) as a side effect of the password-reset flow. Confidence: 0.90
- During password-reset flows, do NOT use session-requiring framework APIs (e.g., `auth.api.changePassword`) — the user is not authenticated. Instead, use the framework's own crypto utilities (e.g., `hashPassword` from `better-auth/crypto`) to hash the password and update the underlying account store directly via the data layer (e.g., Prisma `account.updateMany`). This maintains password-hash compatibility without needing a session. Confidence: 0.70
- Email-based action links (password reset, email verification) should point users to the **web app** origin, not the API origin. The web page then calls the API validation endpoint via fetch. Use `WEB_ORIGIN` and `API_URL` env vars (with sensible localhost defaults) so the callback can rewrite the URL. Follow the pattern established by the existing verification-email-callback. Confidence: 0.80
- Data-access/DB packages should be pure persistence (CRUD, ownership scoping, transactions). Validation, normalization/response-shaping, and business logic belong in the consuming API layer — not in the DB package. This applies universally: domain entities AND infra concerns (billing plans, audit logs, account updates, usage counts). The db package is mechanically thin; the API owns all decision logic ("why" vs "what"). When refactoring, move validation and normalization out of the data layer into the API; the DB package's job is to talk to the database, nothing more. Confidence: 0.90
- The API must never import or use `prisma` directly — every data access goes through a `@recetario/db` package method. This applies universally: domain entities (recipes, ingredients, presentations) AND infra concerns (billing plans, audit logs, account updates, usage counts, preferences). `prisma` remains exported from `@recetario/db` for the one workspace package that genuinely needs the raw client: `packages/auth` (needs it for Better Auth's `prismaAdapter`). `packages/billing` should also have its prisma calls moved to `@recetario/db` CRUD methods — auth is the sole exception. The boundary: `apps/api` and `packages/billing` are forbidden from importing `prisma`; only `packages/auth` keeps the raw client. Confidence: 0.90
- All `@recetario/db` methods follow a strict `actionNoun` naming convention: `get`, `create`, `update`, `delete` as verb prefixes (e.g., `getRecipe`, `createIngredient`, `updateRecipe`, `deletePresentation`). No `list` prefix — collection reads use `get` too (e.g., `getIngredients`, not `listIngredients`). Domain-specific verbs `duplicate` and `upsert` are also allowed where CRUD verbs don't fit naturally (e.g., `duplicateRecipe`, `upsertUserPreferences`). The db package naming is canonical: when an API handler import name conflicts, the db method name wins and the API import is updated to match. Confidence: 0.90
- Tenant isolation (`ownerId` scoping) must be enforced in the db package as the single enforcement point — every domain CRUD method that touches a tenant-owned record must take `ownerId` as a parameter and scope its `where` clause by it. The API layer must never add `ownerId` manually to queries; it relies on the db method already requiring it. Any existing db reader that lacks `ownerId` scoping (e.g., `getIngredient(id)` without ownerId) is a cross-tenant read hole that must be fixed. Confidence: 0.75
- When the web app dev server proxies `/api/*` to the API worker (common in monorepo setups), rewriting only the origin is insufficient — you must also rewrite the API path prefix (e.g., `/api/auth/reset-password` → `/reset-password`). Otherwise the proxy intercepts the request and forwards it to the API, returning JSON instead of the UI page. Confidence: 0.75
- Seed data scripts (e.g., subscription plan seeding, `syncPlansFromStripe`) belong in the `packages/db` package — the data layer owns seeding, even when the seed involves external API calls (Stripe) alongside CRUD. Domain packages like `packages/billing` should not host seed logic; they call db methods for CRUD but don't own data initialization. Confidence: 0.90
