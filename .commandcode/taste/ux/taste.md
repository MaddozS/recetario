# ux
- Plan-upgrade CTAs / "Actualizar plan" marketing messaging must be scoped to actual plan-limit errors only — never shown indiscriminately on a generic error (e.g., a duplicate-recipe failure). The user expects error feedback to reflect the real cause; a plan-upgrade prompt on an unrelated error is misleading and unacceptable. Confidence: 0.75
- Prefers skeleton screens as the primary loading-state pattern over simple spinners/progress-bars alone or full-page loading overlays. When content is loading asynchronously, show a lightweight skeleton placeholder in the main content area — combined with a thin top progress bar and immediate nav-item pending/active state for layered feedback. Confidence: 0.65
- Error handling should be context-dependent, not one-size-fits-all. Generic failures (network errors, 500s) should soft-fail — stay on the current page with a visible error message. But session/auth failures (expired/invalid session) should redirect to the sign-in page with the error reason clearly shown so the user understands why they were logged out. Confidence: 0.70
- Rejects delayed-loading thresholds for skeletons/progress indicators (e.g., "show only after 150ms"). Timing gates can never be perfectly tuned — if the page loads a moment after the threshold, the user sees blank → skeleton → content in rapid succession, which is worse than a quick flash from instant feedback. Loading indicators should appear immediately on interaction, even on fast loads. Confidence: 0.80
- Prefers comprehensive UX-fix coverage: when fixing an interaction-pattern problem (e.g., dead clicks, missing loading feedback), the fix should extend beyond the primary/obvious paths to cover all interactive controls in the app — sidebar nav, bottom nav, breadcrumbs, cards, edit menus, and save/delete form buttons. Piecemeal "fix the main path and leave the rest" is not acceptable. Confidence: 0.65
- When CSS view-transition animations (e.g., Astro `transition:animate`) conflict with skeleton overlays or other loading-state UI — causing flickering, double-renders, or layout glitches — remove the transitions entirely rather than trying to reconcile them. Clean instant content swaps take priority over decorative animations when the two can't coexist cleanly. Confidence: 0.75
- During client-side soft navigations with skeleton loading states, the stale page content must be hidden (display:none) rather than merely covered by an overlay — otherwise the old content can flash through during the DOM swap. The user expects a clean skeleton → new-content transition with no intermediate flash of the previous page. Confidence: 0.70
- In Astro ClientRouter setups, the `transition:name` directive on content containers triggers the View Transitions API, which captures a snapshot of the old DOM before the swap. That snapshot will preserve old page content and cause flashing regardless of CSS tricks (display:none, overlays). When implementing custom skeleton-based loading UIs, remove `transition:name` from the content slot — it is fundamentally incompatible with clean skeleton→content transitions. Confidence: 0.80
- Text search/filter inputs must be accent-insensitive and case-insensitive — normalize with Unicode NFD and strip diacritics before matching (e.g., "platano" should match "Plátano"). Confidence: 0.85
- When a search/filter is active on a list, keep already-selected items visible even if they don't match the query, so the user never loses sight of their current selection. Confidence: 0.80
- Bulk-selection lists should provide a select-all checkbox with a proper indeterminate state (some-but-not-all selected) and support deselect-all. Confidence: 0.80
- When a feature is broken or not working as desired, disable it completely: hide it from all UI and mark it "coming soon" in pricing/plans consistent with other unfinished features — do not leave it partially visible. Confidence: 0.70
- Prefers reducing page scroll when content grows large: use internal scroll containers (max-height + overflow-y) with sticky controls and progressive disclosure (stages/steps) instead of one long linear page. Confidence: 0.60
- For purely client-side recalculation (no network I/O), keep the debounce short (~60ms) so result updates feel instant, while still batching burst events (e.g., a select-all firing N change events). 150ms felt laggy. Confidence: 0.55
- Prefers a single, unambiguous save action per editing flow — parallel save buttons that do different things (e.g., "guardar costo fijo" vs "guardar receta") confuse the user and should be consolidated or clearly differentiated so it's obvious what each action persists. Confidence: 0.60
- Collection-type sub-entities on a detail page (e.g., recipe fixed costs, presentations) should be managed autonomously: add/edit/delete directly at any time, independent of the parent's edit mode — not gated behind or bundled into the parent's edit flow (which surfaces noisy "cancel/apply/delete" controls just from entering the page). Explicitly wants new features to mirror an established in-app pattern ("como las presentaciones") rather than introduce a novel interaction flow. Confidence: 0.70
- After a successful create/update/delete mutation, the affected in-page UI (e.g., the recipe summary/financial header) must update in place from the mutation response — a full page reload should NOT be required for a saved change to appear. The user expects saved changes to reflect immediately in the current view. Confidence: 0.70
- Successful save/delete mutations should surface a visible success confirmation (e.g., a toast) so the user knows the action persisted — silent success on a mutation leaves the user unsure whether it actually saved. Confidence: 0.65
- Save/delete mutations must show visible in-progress feedback mirroring the established PresentationCard pattern: the save button is disabled and shows an inline spinner + contextual text ("Guardando..."), restoring its original content in `finally`; delete uses a mutation-pending overlay with an "Eliminando…" button state. An absent loading state on a mutation is considered a bug ("el loading no funciona"). Confidence: 0.70
- Spanish user-facing copy must be grammatically correct, including accents ("límite", "más") — a typo inherited from the legacy implementation should be corrected, not preserved verbatim for the sake of parity. Confidence: 0.6
- Display elements carrying data (e.g., a unit-cost pill like "$25.00 / kg") should render on a single line (`whitespace-nowrap`); surface fixes are applied when measured in the real DOM to be cost-free, and rejected when they introduce a new layout regression — e.g., forcing `nowrap` on table headers was dropped because it pushed the table into horizontal scroll. Confidence: 0.55
- Server-backed user preferences (theme, accent, etc.) should persist from every authenticated surface that changes them — including incidental toggles (e.g., the landing theme toggle), not only the dedicated Settings save button — with the local preview rolled back if the save fails. The user explicitly chose this maximal consistency over confining persistence to the Settings screen. Confidence: 0.6
- Never render totals computed from data that is still loading: keep skeletons for the affected results panel until the missing records arrive, and if that fetch fails show an inline alert with a retry instead of silently dropping the item from the calculation (the legacy page had no such path, so it just showed incomplete figures). Confidence: 0.55
- A primary action that would be a silent no-op (e.g. "Calcular producción" with nothing selected) should be rendered disabled so the state is legible, rather than enabled and quietly doing nothing as the legacy page did. Confidence: 0.5
- Treats accessibility as a first-class quality gate, not a nice-to-have: automated axe scans across public, auth and private surfaces at both 375 and 1280 with zero serious/critical violations, and real contrast debt (semantic tokens, landing labels/stats, badges, CTAs) fixed in-session rather than waived. The sweep must also cover the full theming matrix — every accent family × light/dark, driven by the presentation cookies — on the surfaces where accents paint text and backgrounds, instead of stopping at each surface's default accent. Scans must measure the settled page (neutralize entrance animations, force revealed state) so they don't report false contrast from mid-animation opacity. Confidence: 0.65
- Accent-colored text must clear AA contrast in both themes with the project's token mapping: on `accent-50` tints use the darkest shades (`accent-700`/`accent-800`), on neutral surfaces `accent-700`, and neutral labels sitting on tinted boxes should use the stronger semantic token (`text-secondary-foreground`) rather than `text-muted-foreground`. Contrast failures are fixed in the components (never by weakening the automated gate). Confidence: 0.55
- A page whose baseline renders an empty container (e.g. a recipe with no ingredients) should show an explicit empty state (icon + message + guidance on how to add the data) in both mobile and desktop layouts — silent empty regions are considered a defect, not parity. Confidence: 0.6
- Instant-feedback rule refined: what is rejected is a *delay before showing* an indicator (e.g. a 150 ms show-throttle), not a floor on how long it stays. A navigation-pending state may be held for a minimum visible window (~500 ms) so that even a fast navigation is perceived as having responded. Confidence: 0.5
- App-header composition: the brand block (logo + app name) comes first and the breadcrumbs follow it — never breadcrumbs before the logo, which the user flagged as a regression. The brand area shows only the app name ("KitchCalc"); its tagline/subtitle ("Costeo Inteligente") is to be dropped rather than shown under the name. Confidence: 0.6
- Expects theme parity for the accent/brand color: the accent ("Coral") must look as similar as possible in dark mode as in light mode. The action fill that carries text (primary button, active nav item, landing CTA band) must keep the same tone in both themes instead of the dark mapping lightening it into a different color family (a deep coral flipping to a salmon fill with a near-black label reads as "another brand"). Where the dark mapping must be overridden for that parity, it applies to the fill role only — text/tint shades keep their normal dark mapping so contrast on tinted surfaces isn't broken. Confidence: 0.7
- Expects the accent theming requirement to generalize across every accent family and both themes, not just the family that exposed the bug: the fix should be a per-family/per-theme rule (the action fill chosen by measurement, e.g. stepping one shade lighter when it fails its minimum contrast against the dark page background) instead of a special case, and the public/marketing surfaces that force the brand accent are expected to be handled by that same role model rather than by a second parallel mechanism. Confidence: 0.65
- The adopted action-fill rule (accepted by the user as the invariant for every accent family): the fill starts at the family's `700` in light; dark keeps that exact same `700` (the accent is the constant, neutrals are what change) and only steps up to the `600` when the `700` does not clear 3:1 against the dark page background; the label on the fill is white in both themes. Simultaneously, the shade ramp (`50…950`, used for ink/tint/border/decoration) must keep its plain dark mapping with NO per-family overrides — the fill role and the ink/tint role are two separate things, and a fix applied to one must not leak into the other. Confidence: 0.65
- Expects parity across the parallel/duplicate surfaces that render the same element: when a UI change is applied to one variant (e.g. dropping the tagline from the desktop header brand), the same change must be carried to every sibling surface showing it (the mobile drawer header), even surfaces only reachable in another state — the user answers "ahí sí debe haber paridad". A remaining inconsistent instance counts as unfinished work. The same expectation drives defect reports: the user shows the broken rendering plus the correct instance used elsewhere as the spec ("tomando de ejemplo como se usa en otros lados") and expects the two made identical, not a new design. Confidence: 0.65
- On a Settings-style form, picking a theme/accent is a live *preview*, not a persisted change: the color must update instantly across the app while that control's surface is visible, but it must NOT survive leaving that surface — changing tab, leaving Settings or reloading reverts to the persisted value, and only the explicit "Guardar cambios" (PUT + cookies written from the confirmed response) persists. The user endorsed binding the preview's lifetime to the section's visibility (unmounting the Preferences section on tab change, i.e. `v-if` instead of `v-show`, so the draft/preview reset coincides exactly with leaving the tab). The reported bug is precisely a form that re-shows the old persisted value while the app keeps painting the leaked preview: displayed value and applied appearance must always agree. Confidence: 0.7
- Left accent bars (the thick left border on cost/financial rows and cards) must render as straight, full-height lines like the `FinancialSummary` rows: square on the bordered side, rounding allowed only on the right (`rounded-r-xl`, never `rounded-xl`) — a border-radius on the bordered side curls a 3px border into a splinter and breaks the look the user expects ("como se usa en otros lados"). The role→border-class mapping is expected to be a single shared source consumed by every surface that paints a bar, so the two can't drift in color or geometry. Confidence: 0.55
- The automated a11y gate must account for what axe cannot decide: text over a `background-image`/gradient lands in `incomplete` (not `violations`) and would otherwise stay silently green. Every `color-contrast` incomplete node must be documented in the spec (rule + stable region anchor such as `#how-it-works`/`[data-landing-hero]`, reason, and the ratio actually measured), and a pixel-based contrast probe (rendered-pixel sampling under each line box, worst sampled point decides the node) must judge those nodes — and the real AA failures the probe surfaces are fixed in the tokens/components, never absorbed into the allowlist (another allowlist entry = another silent hole). Confidence: 0.6
- The accent's *text* role is a first-class token emitted apart from the shade ramp (`--aw-accent-text` / `--color-accent-text`): in light it is the family's `800`, in dark the tone that `800` maps to (`300`), with a unit test locking ≥4.5:1 across the 7 families × 2 themes over the page background and the secondary surface. Icons and decorative accent keep the plain ramp (their threshold is 3:1), and the role exists so ink, fill and tint can't drift. Confidence: 0.6
- When the same object is rendered on two surfaces (e.g. the plan card on the landing and on `/pricing`), its substrate — border, background, radius, padding-by-density — belongs to one shared shell component, while everything surface-specific (container/scroller layout, hover, focus, disabled states) stays in each consumer; the transient variant (deep-link highlight) takes precedence over the permanent one (recommended plan), and skeletons mount the same shell so the loading state already has the final shape. Each variant maps to exactly one border-color class: never stack `border-border` with `border-accent-*`, because Tailwind resolves same-property conflicts by stylesheet order, not by attribute/class order. Confidence: 0.6
- The marketing hero must carry real product proof — a capture of the real app (real seeded data, with the cost metrics legible) — instead of a decorative brand logo, and it must sit in the first viewport at both desktop and mobile widths (on mobile reordered after the CTAs and before the cost card) rather than living a screen and a half further down at a scale where the numbers can't be read. Confidence: 0.5
- Utility classes must be checked against the token definitions: a class with no matching token in `@theme`/`tokens.css` (e.g. `shadow-accent-tint`, sibling of the `accent-950` finding) compiles to nothing — dead code that never painted, must not be carried over into a new component, and its remaining usages get reported with a named owner rather than silently copied. Confidence: 0.6
- The two public plan surfaces have different jobs and must not duplicate each other: the marketing landing is the *decision* surface (each card shows a handful of differentiators + price + CTA + a link to the detail), while `/pricing` is the *comparison* surface (only the rows that change between plans, with the rows that are identical across plans listed once rather than the whole catalog repeated per plan). Cloning the full catalog onto both surfaces is the defect being fixed, and dense ERP-style tables are rejected by the product voice. Confidence: 0.6
- A selling surface shows what the visitor *gains* — the included, already-available features that the free plan does not already give — and never the excluded rows or the "coming soon" promises. If the list is trimmed, the copy says it in text ("y N funciones más") so a card never pretends to be the whole catalog. Confidence: 0.55
- Responsive layouts must preserve desktop/mobile information parity: a mobile reachability problem is solved by reordering the DOM (the recommended plan first so it needs no swipe), never by hiding, collapsing or dropping content, and the DOM order must match the visual order so keyboard tab order agrees with what is seen. Confidence: 0.6
- A new surface must be assembled from the app's existing design vocabulary, not a bespoke treatment: the user's acceptance test is literally whether it "looks like part of the system" — a `Card` with a real card header (accent icon + `font-display text-base font-bold` title), `Badge` for scope/metadata, and the tinted accent surface (`bg-accent-50` / `border-accent-200` / `accent-800` ink) for the emphasized answers, the same resources the metric pills and category badges already use. Emphasis by tinted surface is preferred over accent ink sprinkled on individual numbers, and a header that carries the same hierarchy as the block's own row labels reads as outside the system. Confidence: 0.6
- A financial/summary block is judged by whether it tells its story: labelled tiers (e.g. "Costo de la mezcla" / "Precio de venta"), the lever rendered with the section it governs (the editable margin — later refined to sit in the section header, leaving the answer band to hold only the outcomes), and the figures the product actually promises. A flat list of sibling values — the margin sitting as one more peer number — is rejected as "no se entiende", and the same quantity must keep one name across plan variants (never "Costo Total Real" vs "Costo Total Receta", or "Margen Deseado" vs "Margen Utilidad"). Confidence: 0.55
- In a financial/summary answer band, the cell labels are clean uppercase text with no icons or symbols attached to them; arithmetic operators (`+`, `=`) live only in the cost lane, where they actually state the sum. A symbol on a label or on a figure as decoration is rejected ("solo los textos superiores sin iconos/símbolos"). Confidence: 0.55
- The governing control of a section (e.g. the editable margin lever) belongs in the section header — label on the left, control on the right, mirroring the ingredients card's "title ⋯ action" pattern — so the highlighted result band stays self-contained with no controls inside it. Confidence: 0.55
- The small line under a headline figure must earn its place by saying what the figure is or means (e.g. "Lo que cuesta producir", "Con 30% de margen", "≈ $48.12 por mezcla"); a subtitle that restates nothing is rejected and must be rewritten to something that makes sense. Confidence: 0.5
- A bar pinned over scrolling content (e.g. the production results toolbar) must be fully opaque: no alpha (`bg-card/95`) and no `backdrop-blur`. The opaque band must also span the whole edge of the scroll container — including the container's own padding, compensated with negative margins plus matching padding and a `-top-*` offset — so rows never show through the bar itself, its rounded corners or the gap above it. Any content visible behind a pinned bar is treated as a bug ("al tener un espacio se ve por detrás las tablas"). Confidence: 0.6
