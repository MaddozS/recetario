# Research: Página de Registro de Usuario

**Feature**: 005-sign-up-page | **Date**: 2026-05-27

## 1. Better Auth Custom User Fields (`firstName`, `lastName`)

### Decision

Use Better Auth's `additionalFields` configuration on the `user` object in `src/lib/auth.ts`. Add `firstName` (required) and `lastName` (required) fields.

### Rationale

Better Auth natively supports extending the User model via `user.additionalFields`. These fields are:
- Type-safe: TypeScript infers them automatically from the config.
- Available in all auth operations (`signUp.email`, `signIn`, `useSession`).
- CLI-aware: `npx auth@latest generate` can generate the Prisma schema changes. For this project we'll add columns manually to the Prisma schema and run `npx prisma migrate dev`.

The existing `name` field is kept (required by Better Auth's core User schema) and will be set to `firstName + " " + lastName` as a computed display name.

### Alternatives Considered

- **Custom separate table**: Overkill for two string fields. Better Auth wouldn't return them in session data.
- **JSON column**: Would break type safety and queryability.
- **Use only `name` field and split client-side**: Loses structured data, cannot sort/filter by last name.

### Implementation

```typescript
// src/lib/auth.ts
export const auth = betterAuth({
  user: {
    additionalFields: {
      firstName: { type: "string", required: true },
      lastName: { type: "string", required: true },
    },
  },
  // ... rest of config
});
```

```prisma
// prisma/schema.prisma — new columns on User model
model User {
  firstName String  @map("first_name")
  lastName  String  @map("last_name")
  // ... existing fields (name, email, etc.)
}
```

## 2. Google Sign-Up (Account Creation via Social Provider)

### Decision

Change `disableSignUp` from `true` to `false` on the Google social provider. Add `mapProfileToUser` to populate `firstName`/`lastName` from Google profile data.

### Rationale

The current `disableSignUp: true` was set for the sign-in page spec (004) to prevent auto-creation of accounts on the sign-in page. With this setting, Google cannot create accounts anywhere — including the sign-up page where it's explicitly required.

Setting `disableSignUp: false`:
- Enables Google account creation on the sign-up page (FR-013).
- Enables Google account creation on the sign-in page too (auto-creates if account doesn't exist). This is the standard UX pattern across most SaaS apps. The sign-in page already handles all error codes gracefully.
- The original sign-in page spec FR-010 (no auto-create) is effectively superseded by this more pragmatic approach. The `sign-in.astro` error handler for `signup_disabled` code becomes a no-op and can be removed.

### Alternatives Considered

- **Keep `disableSignUp: true` + custom server endpoint for sign-up**: Requires building a custom OAuth flow, adding complexity and maintenance burden.
- **Two separate Google provider configs**: Not supported by Better Auth (one config per provider).
- **Database hook with intent parameter**: Possible but adds complexity (passing state through OAuth callbacks) without clear benefit.

### Implementation

```typescript
// src/lib/auth.ts
socialProviders: {
  google: {
    clientId: process.env.GOOGLE_CLIENT_ID!,
    clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
    disableSignUp: false,  // Changed from true
    mapProfileToUser: (profile) => {
      return {
        firstName: profile.given_name,
        lastName: profile.family_name,
      };
    },
  },
},
```

## 3. Google Profile Field Mapping

### Decision

Map Google's `given_name` → `firstName` and `family_name` → `lastName` via `mapProfileToUser`.

### Rationale

Google's OAuth2 `/userinfo` endpoint returns `given_name` (first name) and `family_name` (last name) as standard claims. Better Auth's `mapProfileToUser` receives these directly from the Google profile response.

### Edge Cases

- User has no last name in Google profile (single name cultures): `family_name` may be `undefined`. Fallback to empty string or use `given_name` as both first and last name.
- Google returns names with accented characters: handled natively (UTF-8).

## 4. Prisma Schema Migration

### Decision

Add `firstName` and `lastName` columns to the `User` model. Generate migration via `npx prisma migrate dev --name add_first_last_name`.

### Rationale

Manual Prisma schema change + migration is the standard workflow for this project. No need for `npx auth@latest generate` since we control the Prisma schema directly.

The `name` field is retained as a computed display name (not stored directly — Better Auth's `databaseHooks.user.create.before` can set it from `firstName + " " + lastName`).

### Implementation

```sql
-- Migration (generated by Prisma)
ALTER TABLE "user" ADD COLUMN "first_name" TEXT NOT NULL DEFAULT '';
ALTER TABLE "user" ADD COLUMN "last_name" TEXT NOT NULL DEFAULT '';
```

Note: Adding NOT NULL columns with defaults to an existing table. If there are existing users, the migration script will need to handle the name split from the existing `name` field.

## 5. Client-Side Sign-Up Function Update

### Decision

Update `signUpWithEmail` in `src/lib/sign-in.ts` to accept `firstName` and `lastName`, and construct the `name` field as `firstName + " " + lastName`.

### Rationale

Better Auth's `signUp.email` expects a required `name` field (core schema) and optional `additionalFields`. We pass both:
- `name`: computed display name
- `firstName`, `lastName`: via additional fields

### Implementation

```typescript
// src/lib/sign-in.ts
export async function signUpWithEmail(
  email: string,
  password: string,
  firstName: string,
  lastName: string,
) {
  const { error } = await authClient.signUp.email({
    email,
    password,
    name: `${firstName} ${lastName}`,
    firstName,
    lastName,
  });
  if (error) throw error;
}
```

## 6. Google Sign-Up Client Function

### Decision

The existing `signInWithGoogle` function in `src/lib/sign-in.ts` works for both sign-in and sign-up with `disableSignUp: false`. No new function needed.

### Rationale

Better Auth's `signIn.social` with `disableSignUp: false` handles both cases transparently:
- If Google account already linked → signs in
- If Google account not linked → creates account and signs in

The sign-up page can call `signInWithGoogle()` (the same function the sign-in page uses). The `callbackURL` should redirect to `/recipes` after sign-up (or respect the `redirect` param).
